# Contributing

## Установка окружения

```bash
pip install -r requirements.txt       # pydantic>=2.0
pip install -r requirements-dev.txt   # pytest>=7.0
```

## Тесты

```bash
pytest tests/ -v
```

Тесты разделены по зависимостям намеренно:

- `tests/test_graph_utils.py` работает на чистых Python-объектах (простой
  класс `Node` с полями `id/children/parents`) и не импортирует pydantic.
  `graph_utils.py` импортирует `BaseNode` только под `TYPE_CHECKING`, так
  что модуль физически не тянет за собой pydantic — тест это подтверждает.
- `tests/test_core.py` использует настоящий `GraphEngine`/`BaseNode` и
  требует установленного pydantic.

Если вы правите `graph_utils.py`, проверяйте, что изменение не вводит
скрытую зависимость от pydantic — иначе `test_graph_utils.py` перестанет
быть «лёгким» тестовым контуром, ради которого он так устроен.

## Соглашения, которых придерживается существующий код

Эти пункты не задокументированы отдельно в исходном репозитории — они
выведены из самого кода как наблюдаемые соглашения. Следуйте им, чтобы
новый код не выделялся на общем фоне.

- **Итеративные алгоритмы, не рекурсивные.** Любой обход графа
  (`GraphUtils.walk`, поиск циклов, `GraphEngine.collapse`) написан через
  явный стек/очередь, а не через рекурсию Python. Причина — не стиль, а
  реальный предел рекурсии, который задевают графы на тысячи узлов (см.
  `docs/design_decisions.md`).
- **Один декоратор ошибок вместо copy-paste try/except.** Публичные методы,
  которые должны транслировать неожиданные исключения в исключение из
  `fsm_core.exceptions`, оборачиваются `@wrap_errors(SomeError,
  passthrough=(...))` из `fsm_core/_errors.py`, а не переопределяют
  try/except вручную.
- **Иерархия исключений.** Любое новое исключение пакета наследуется от
  `CoreError` (или от соответствующей ветки — `GraphError`,
  `EventBusError`, `PluginError`), а не от `Exception` напрямую.
- **Логирование с префиксом-тегом.** Сообщения логов помечаются коротким
  тегом подсистемы в квадратных скобках: `[ENGINE]`, `[NODE]`, `[UTILS]`,
  `[EVENT_BUS]`, `[REGISTRY]`, `[DISPATCHER]`. Логгер получается через
  `logging.getLogger(__name__)` на уровне модуля.
- **Identity, не value, для узлов.** Если вы добавляете новое поле в
  `BaseNode`/`BasePipeline`, не полагайтесь на дефолтное сравнение pydantic
  — оно уже переопределено на сравнение по `id` намеренно (см.
  `docs/graph_model.md`). Не возвращайте это поведение обратно.
- **`parents`/`children` исключены из сериализации.** Оба поля объявлены с
  `Field(..., exclude=True)`, потому что содержат циклические ссылки друг
  на друга и не сериализуются в JSON/`model_dump()` напрямую. Если вы
  добавляете новое поле, которое тоже может участвовать в цикле ссылок —
  подумайте о том же.
- **Плоские, «доменные» сообщения об ошибках.** Исключения поднимаются с
  человекочитаемым текстом («Cannot add node as its own child», а не
  кодом ошибки), это уже используется в тестах через `pytest.raises`.

## Регресс-тесты для найденных багов

Каждый исторический баг, исправленный в этой кодовой базе, сопровождается
тестом с docstring, объясняющим, что именно было не так (см.
`tests/test_core.py`). Если вы исправляете баг — добавляйте тест в этом же
формате: короткое имя, docstring с сутью бага, минимальный воспроизводящий
сценарий. Это то, что уже отличает данный репозиторий от типового: баг без
регресс-теста в нём считается неисправленным.

## Чего в проекте пока нет

Нет `LICENSE`, нет CI-конфигурации, нет `pyproject.toml`/`setup.py` — пакет
не оформлен как устанавливаемый дистрибутив (`pip install -r
requirements.txt` подключает зависимости, но не сам пакет; локальный запуск
предполагает работу из корня репозитория). Если ваш вклад — именно
упаковка проекта, полезно явно обсудить это перед PR, поскольку это меняет
то, как остальной код импортируется в потребляющих проектах.
