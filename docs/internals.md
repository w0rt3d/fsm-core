# Internals

Этот документ описывает поведение «под капотом» — то, что не обязательно
знать для обычного использования библиотеки, но важно при отладке или
модификации кода.

## Инициализация `GraphEngine`

```python
def __init__(self, max_history: int = 1000):
    self._nodes: Dict[str, BaseNode] = {}
    self._root: Optional[BasePipeline] = None
    self._registry = PluginRegistry()
    self._event_bus = EventBus(max_history=max_history)
    self._dispatcher = EventDispatcher(self._event_bus, self._registry)
    self._context_manager = ContextManager()
```

Порядок создания важен: `EventDispatcher` создаётся **после** `EventBus` и
`PluginRegistry`, потому что его конструктор сразу подписывается на все
события из `_HOOK_TABLE`:

```python
def __init__(self, event_bus, registry):
    self._event_bus = event_bus
    self._registry = registry
    self._register_all_hooks()   # подписка происходит немедленно
```

Практическое следствие: **с момента создания `GraphEngine()` мост
событие → хук плагина уже настроен**, даже если ни один плагин ещё не
зарегистрирован. `create_node`/`create_pipeline`, вызванные до
`register_plugin`, всё равно публикуют `node_created`/`pipeline_created` —
эти события просто попадают в историю `EventBus` и проходят через
`EventDispatcher`, который на пустом `PluginRegistry` вызывает `call_hook`
без единого активного плагина (`_active_plugins()` — пустой генератор,
цикл не выполняется ни разу).

## Регистрация и готовность плагина

1. `engine.register_plugin(plugin)` → `PluginRegistry.register(plugin)`:
   - если `plugin.name` уже занят — no-op с предупреждением;
   - иначе: `_plugins[plugin.name] = plugin`, вызывается
     `plugin.on_register(self)`, затем все пары из
     `plugin.get_extensions()` копируются в `_extensions`.
2. `engine.ready()` → `PluginRegistry.ready()`:
   - `_is_ready = True`;
   - для **каждого** зарегистрированного плагина (не только активных —
     `enabled`/`is_quarantined` здесь не фильтруют) вызывается
     `plugin.on_ready()`; исключение внутри — логируется, не прерывает
     обработку остальных плагинов.

`_is_ready` нигде дальше не читается кодом `PluginRegistry` — флаг
устанавливается, но не используется как условие для чего-либо ещё в
текущей реализации (например, не блокирует `call_hook` до вызова
`ready()`). Хуки можно получать и до `ready()`, если события начинают
публиковаться раньше.

## Выполнение (полный путь `emit` → хук плагина)

1. `GraphEngine`-метод (например, `add_node`) мутирует структуру графа
   напрямую (`pipeline.add_child(node, index)`), **до** публикации
   события — то есть к моменту, когда плагин получает `on_node_added`,
   изменение в графе уже фактически произошло.
2. `self._event_bus.emit(event_name, data={...})`:
   - создаётся `Event`, добавляется в `_history` (кольцевой буфер);
   - обработчики события (`_subscribers[event_name]`, отсортированы по
     `EventPriority` заранее, на этапе `subscribe`) вызываются по очереди;
   - для встроенных событий `_HOOK_TABLE` единственный обработчик — тот,
     что зарегистрировал `EventDispatcher` в своём конструкторе.
3. Обработчик `EventDispatcher._dispatch(event_name, hook_name, keys,
   use_bool, data, context)`:
   - достаёт из `data` каждый ключ из `keys`; если обязательный ключ
     отсутствует (`None` и не в `_OPTIONAL_KEYS`) — логирует
     предупреждение и **не вызывает** хук вообще (тихий пропуск, не
     исключение);
   - вызывает `self._registry.call_hook(hook_name, *values, context)`
     (или `call_hook_bool` для `pipeline_validated`).
4. `PluginRegistry.call_hook(hook_name, *args)`:
   - через `_active_plugins()` перебирает плагины в порядке `priority`
     (по возрастанию), пропуская квалифицированных и `enabled=False`;
   - через `_resolved_hooks` для каждого активного плагина через
     `getattr(plugin, hook_name, None)` резолвит метод;
   - вызывает `_call(plugin, method, args)`, которая при успехе отмечает
     `plugin._record_success()`, при исключении — `plugin._record_error(e)`,
     логирует и **пробрасывает** исключение — но вызывающий
     `call_hook`/`call_hook_bool` его тут же ловит `except Exception:
     continue` и переходит к следующему плагину.

Итог: одна публикация события `emit()` может привести к вызову хука на
десятках плагинов, каждый из которых изолирован от ошибок соседей на двух
независимых уровнях (внутри `PluginRegistry._call` и внутри
`EventBus.emit`, который тоже ловит исключения обработчиков верхнего
уровня — в данном случае самого `EventDispatcher`-обработчика).

## Остановка / завершение

В коде нет метода `shutdown()`/`close()`/`stop()` ни у `GraphEngine`, ни у
`EventBus`, ни у `PluginRegistry`. Жизненный цикл этих объектов совпадает
с жизненным циклом обычных Python-объектов — заканчивается вместе со
сборкой мусора/выходом из области видимости. `BasePlugin.on_unregister`
объявлен как хук, но вызвать его сейчас нечем — в `PluginRegistry` нет
метода `unregister` (см. `plugins.md`).

## Распространение событий: карантин плагина в реальном времени

Карантин проверяется на **каждый** вызов `call_hook*`, а не кешируется на
время одного `emit`. Если плагин уходит в карантин *во время* обработки
одного события (например, третий подряд неуспешный вызов `on_node_added`
для этого конкретного `emit`), это не откатывает уже случившиеся вызовы
для других плагинов в рамках этого же `emit` — карантин влияет только на
**следующие** вызовы `call_hook*` (следующее событие или следующий хук),
не на уже выполняющийся.

## Структурные перестройки — пошагово

### `simplify(pipeline)`

Рекурсивная (через обычный вызов функции Python, не через явный стек —
единственная из четырёх структурных операций, которая не итеративна;
глубина рекурсии здесь равна глубине графа, а не его размеру, что на
практике почти всегда значительно меньше 1000) функция `_simplify(node)`:

1. Сначала рекурсивно упрощает каждого ребёнка (`node.children[i] =
   _simplify(child)`).
2. Затем проходит по `node.children` слева направо:
   - если ребёнок — не `BasePipeline`, пропускается;
   - если `BasePipeline` без детей — удаляется из `node.children`, из
     `child.parents` убирается `node`, узел удаляется из
     `self._nodes`;
   - если `BasePipeline` ровно с одним ребёнком — на месте `child` в
     `node.children` подставляется этот единственный внук, у внука
     `parents` переключается с `child` на `node`, сам `child` очищается
     (`parents.clear()`, `children.clear()`) и удаляется из `_nodes`.
3. В конце — одно `graph_changed`.

### `expand(node, children)`

1. Создаёт новый `BasePipeline(id=node.id)` — **с тем же id**, что у
   заменяемого листа. Это значит, что `engine.get_node(node.id)` после
   `expand` найдёт уже новый пайплайн, не исходный узел.
2. Каждый элемент `children` добавляется в новый пайплайн через
   `pipeline.add_child(child)` и регистрируется в `self._nodes`.
3. Все бывшие родители `node` перевешиваются на новый `pipeline` (замена в
   списке `parent.children`), все бывшие дети `node` — аналогично.
4. `node.parents`/`node.children` очищаются, `node` удаляется из
   `self._nodes` (сам объект `node` остаётся валидным Python-объектом,
   просто отвязанным от графа и от реестра).
5. Если `node` был корнем графа (`self._root.id == node.id`) — корень
   переключается на новый `pipeline`.

**Наблюдение, подтверждённое трассировкой, а не только чтением кода**:
поскольку `pipeline = BasePipeline(id=node.id)` создаётся с **тем же**
`id`, что и заменяемый узел, строка `self._nodes[pipeline.id] = pipeline`
(шаг 2) и более поздняя `self._nodes.pop(node.id, None)` (шаг 4) обращаются
к **одному и тому же ключу словаря** (`pipeline.id == node.id`). Вторая
операция удаляет запись, оставленную первой, — то есть после `expand()`
результирующий `pipeline` физически присутствует в графе (он
корректно подключён к бывшим родителям/детям `node`, найдётся через
`find_node`/`get_flat_list`/обход от корня), но **отсутствует в реестре
`self._nodes`**, а значит `engine.get_node(node_id)` после `expand()`
вернёт `None`, хотя узел с этим `id` явно существует в графе. Тест
`test_expand_preserves_connections` этого не ловит, потому что проверяет
только `child_old.id not in e._nodes` — что технически верно и для
«узел корректно зарегистрирован под новым объектом», и для «узел вообще
пропал из реестра»; оба случая дают одинаковый результат этой конкретной
проверки. Это задокументированное здесь ограничение поведения `expand()`,
а не исправление — правка самого кода не входит в задачу документирования
существующей библиотеки.

### `collapse(node)`

Итеративный post-order обход (явный стек `[(node, visited_flag)]`):

1. При первом посещении узла — кладёт его обратно с флагом `visited=True`
   и добавляет всех его текущих детей в стек с `visited=False` (снизу
   вверх).
2. При повторном посещении (`visited=True`, дети уже обработаны): для
   каждого прямого ребёнка `current` — все родители этого ребёнка, кроме
   самого `current`, перевешиваются на `current` (то есть «внуки»
   поднимаются на уровень схлопываемого узла), ребёнок удаляется из
   `self._nodes`, у него очищаются `parents`.
3. В конце `current.children.clear()`.

Итог: всё поддерево `node` пропадает из графа и из `self._nodes`, `node`
остаётся с пустыми `children`.

### `replace_node(old_node, new_node)`

Прямая замена без обхода поддерева: все прямые родители и дети
`old_node` перевешиваются на `new_node` (по одному уровню связей, не
рекурсивно — поддерево `new_node` не строится из поддерева `old_node`,
`new_node` просто занимает то же место в графе). `old_node` очищается и
удаляется из `_nodes`, `new_node` в него добавляется. Если `old_node` был
корнем — корень переключается на `new_node`, но **только если** `new_node`
— экземпляр `BasePipeline`; иначе `self._root` становится `None` (граф
временно остаётся без определённого корня, пока не будет создан или
назначен новый).
