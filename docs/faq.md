# FAQ

### Почему пакет называется `fsm_core`, если это не конечный автомат?

Название — историческое, и в текущем коде **нет никакой реализации FSM**:
нет типа «состояние», нет описания допустимых переходов, нет guard-условий,
нет валидации «из состояния A нельзя перейти в состояние C». Событие
`node_changed`/метод `notify_changed` переносят `old_state`/`new_state`
как непрозрачные словари, которые целиком формирует и интерпретирует
вызывающий код — библиотека их не читает и не проверяет. По факту
`fsm_core` — DAG-движок с шиной событий и системой плагинов. Если вам
нужен именно конечный автомат — этот пакет даёт для него разве что
структурный каркас хранения графа состояний и уведомления о переходах, но
не логику самого автомата.

### `engine.execute(pipeline)` реально выполнит мои задачи?

Нет. Он валидирует граф на циклы и публикует событие `pipeline_executed`.
Если вы ждёте, что `fetch`/`transform`/`load` из примера в README
реально вызовутся, — это будет происходить только внутри обработчика,
который вы сами подпишете на `pipeline_executed` (обычно — через
`on_pipeline_executed` плагина). Подробности —
[execution_flow.md](execution_flow.md).

### Как получить порядок задач для реального исполнения (топологическая сортировка)?

В `GraphUtils` нет топологической сортировки как отдельного метода.
`walk(root, mode="dfs")`/`walk(root, mode="bfs")` дают DFS/BFS порядок
обхода дерева/DAG от корня, что для дерева совпадает с валидным порядком
«родитель раньше детей», но это не то же самое, что топологическая
сортировка произвольного DAG с несколькими родителями у одного узла —
`walk` не проверяет, что все родители узла уже посещены, прежде чем
посетить сам узел (посещение определяется исключительно порядком обхода
от единственной точки старта). Если вам нужна именно топологическая
сортировка с учётом множественных зависимостей — её нужно реализовать
отдельно, поверх `node.parents`/`node.children`.

### Плагин ушёл в карантин — как узнать почему?

```python
plugin = engine.get_plugin("my_plugin")
plugin.is_quarantined()          # bool
plugin.error_count()             # int
plugin._health.quarantine_reason # str, если хочется прочитать текст причины
plugin._health.last_error        # исходное исключение
```

`quarantine_reason`/`last_error` — атрибуты `PluginHealth`, доступного
через приватный (по соглашению об именовании, не по факту защиты Python)
атрибут `plugin._health`. Публичного метода-геттера для причины карантина
`BasePlugin` не предоставляет.

### Можно ли настроить `max_errors` для конкретного плагина?

Не через параметры `BasePlugin.__init__()` — он их не принимает. Нужно
переопределить `__init__` в своём плагине и создать `PluginHealth` с нужным
порогом вручную:

```python
from fsm_core import BasePlugin
from fsm_core.plugins import PluginHealth

class TolerantPlugin(BasePlugin):
    name = "tolerant"
    version = "1.0"

    def __init__(self):
        super().__init__()
        self._health = PluginHealth(max_errors=10)
```

### Как снять плагин с карантина?

`plugin.reset_health()` на самом объекте плагина — не через
`PluginRegistry`, у него такого метода нет (см. `plugins.md`).

### `error_count()` считает ошибки подряд или всего?

Всего, накопительно, за всю жизнь плагина. Успешные вызовы между ошибками
не сбрасывают счётчик — сбрасывает только явный `reset_health()`. Название
из README/комментариев («после N *последовательных* ошибок») не совсем
точно отражает реализацию — см. подробный разбор в
[plugins.md](plugins.md#pluginhealth--circuit-breaker).

### Почему `on_node_removed`/`on_node_moved` у меня не вызывались (в старых версиях кода)?

Это исторический баг, уже исправленный: диспетчер читал не те ключи из
`event.data`, что публиковал `engine.py`. См. `CHANGELOG.md`. В текущей
версии оба хука вызываются корректно (покрыто тестом
`test_node_removed_and_node_moved_hooks_actually_fire`).

### Почему `GraphUtils.get_depth` дал число меньше, чем я ожидал?

`get_depth` идёт только по `children[0]` на каждом уровне — это глубина
одной конкретной ветки, не максимум по всем веткам дерева. Если самая
длинная ветка вашего графа не является первым ребёнком ни на одном уровне
— результат будет заниженным. См. [traversal.md](traversal.md).

### `EventBus`/`ContextManager` потокобезопасны?

Нет. Ни `EventBus._subscribers`/`_history`, ни `ContextManager
._current_context` не защищены блокировками и не используют
thread-local/contextvars хранилище. В однопоточном коде (в т.ч. обычном
asyncio-коде без конкурентного доступа к одному `GraphEngine`) это не
проблема; при реальном параллелизме — да. Подробнее —
[design_decisions.md](design_decisions.md).

### Могу ли я добавить своё событие, чтобы оно тоже вызывало хук плагина?

Само событие — да, `EventBus.emit("my_event", ...)` не ограничен списком
встроенных имён. Чтобы оно доходило до `BasePlugin`-хуков через
`PluginRegistry`, нужно, чтобы `EventDispatcher._HOOK_TABLE` знал про него
— а эта таблица зашита в `dispatcher.py` и не расширяется извне пакета
(нет публичного API для регистрации новой записи в `_HOOK_TABLE`). Прямая
подписка на `EventBus` без похода через систему плагинов — рабочий путь и
без правки `dispatcher.py`.

### После `engine.expand(node, children)` `engine.get_node(node.id)` возвращает `None` — это баг?

Да, это реальная особенность текущей реализации, а не ожидаемое поведение
по замыслу. `expand()` создаёт новый `BasePipeline` с тем же `id`, что у
заменяемого узла, регистрирует его в `self._nodes`, а затем — на
следующих строках того же метода — удаляет из `self._nodes` запись под
`node.id`. Поскольку `id` у обоих объектов совпадает, это одна и та же
запись словаря: удаление стирает и только что добавленный `pipeline`.
Сам граф при этом остаётся корректным — `pipeline` подключён к прежним
родителям и детям, найдётся через `find_node`/`get_flat_list`/`get_root`,
только не через `get_node`/`_nodes`. Подробный разбор — в
[internals.md](internals.md#expandnode-children).

### Что случится, если два плагина зарегистрируют `get_extensions()` с одинаковым именем?

Второй молча перезапишет первого в `PluginRegistry._extensions` —
коллизии имён не проверяются и не логируются.

### Что случится, если я зарегистрирую два плагина с одинаковым `name`?

Второй `register()` — no-op с предупреждением в лог; первый плагин с этим
именем остаётся в реестре, второй просто не добавляется (и его
`on_register` никогда не будет вызван).

### Библиотека потокобезопасна в целом?

Нет, ни на каком уровне — ни `EventBus`, ни `PluginRegistry`, ни
`GraphEngine._nodes` (обычный `dict`, без блокировок) не проектировались с
расчётом на конкурентный доступ из нескольких потоков. `emit_async`
добавляет конкурентность на уровне *обработчиков одного события*
(`asyncio.gather`), но не защищает общее состояние (`_history`, граф) от
одновременной мутации из разных задач/потоков.

### Есть ли персистентность (сохранение графа на диск/в БД)?

Нет. Всё существует только в памяти процесса. Сериализация pydantic
(`model_dump()`/`.model_dump_json()`) доступна на уровне отдельного
`BaseNode`, но `children`/`parents` из неё исключены (`exclude=True`) —
«из коробки» сериализация не восстановит связи графа, только плоские
поля одного узла.
