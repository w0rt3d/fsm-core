# Traversal (`GraphUtils`)

`GraphUtils` — класс со статическими методами, без собственного состояния и
без экземпляров. Всё в нём — чистые функции `BaseNode -> ...`, не
привязанные к `GraphEngine`. `graph_utils.py` импортирует `BaseNode`
только под `TYPE_CHECKING`, поэтому сам модуль не требует pydantic для
работы — тесты (`test_graph_utils.py`) прогоняют его на простом
Python-классе с полями `id/children/parents`.

## `walk(root, mode="dfs", direction="children", stop_when=None)`

Единая точка входа для обхода. `mode` — `"dfs"` или `"bfs"`, `direction` —
`"children"` или `"parents"` (обход можно вести и вверх по дереву).
`stop_when` — опциональный предикат: если возвращает `True` для узла, узел
всё равно попадает в результат, но его соседи по `direction` **не
раскрываются** (то есть `stop_when` ограничивает *глубину раскрытия*, а не
прерывает весь обход).

### DFS — явный стек

```python
stack = [root]
while stack:
    node = stack.pop()
    if node.id in visited: continue
    visited.add(node.id)
    result.append(node)
    if stop_when and stop_when(node): continue
    stack.extend(reversed(neighbors))
```

`reversed(neighbors)` при push в стек — не случайность: поскольку стек
разворачивает порядок (LIFO), проталкивание соседей в обратном порядке
восстанавливает тот же порядок обхода «сначала первый ребёнок», который
дала бы наивная рекурсивная реализация (`for child in
node.children: dfs(child)`). Без `reversed` порядок обхода был бы
право-налево вместо лево-направо — молча иной результат, не ошибка, но
несовместимость с ожидаемым «естественным» порядком.

### BFS — `collections.deque`

Обычная очередь с посещёнными узлами, помечаемыми **в момент постановки в
очередь**, а не в момент извлечения (иначе один и тот же узел с двумя
путями до него мог бы попасть в очередь дважды).

### Почему итеративно, а не рекурсивно

Явный стек/очередь вместо рекурсии Python — не стилистический выбор.
Собственный бенчмарк библиотеки (`example.py`) строит цепочки от 10 000
узлов; тесты — от 6000. Рекурсивный DFS с одним кадром стека на узел либо
упирается в `sys.getrecursionlimit()` (по умолчанию 1000), либо требует
`sys.setrecursionlimit()`, что просто отодвигает ту же проблему и
дополнительно рискует настоящим переполнением C-стека интерпретатора.
Итеративная версия не имеет предела глубины, определяемого языком, и
измеримо быстрее за счёт отсутствия накладных расходов на вызов функции
Python на каждый узел.

## `find_node(root, node_id)`

Ранне завершающийся DFS с явным стеком: как только `node.id == node_id`,
функция сразу возвращает узел, не обходя остальной граф. Отдельная
реализация от `walk`, а не `walk(..., stop_when=...)` — сознательно, после
того как версия через `stop_when` показала себя некорректной для
ветвящихся графов (см. `CHANGELOG.md`): `stop_when` не прерывает обход
*соседних* веток, только раскрытие *текущего* узла, поэтому не годится для
«найти и сразу остановиться».

## `is_ancestor_of(ancestor, descendant)`

```python
result = GraphUtils.walk(root=descendant, mode="dfs", direction="parents",
                          stop_when=lambda n: n.id == ancestor.id)
return bool(result) and result[-1].id == ancestor.id
```

Идёт от `descendant` вверх по `parents` и проверяет, встречается ли
`ancestor` на этом пути. Это функция, на которой держится вся защита от
циклов в `BaseNode.add_child`/`add_parent` (см. `graph_model.md`) — перед
добавлением связи проверяется, не создаст ли она путь, который уже и так
существует в обратном направлении.

## `get_root(node)`

```python
current = node
while current.parents:
    current = current.parents[0]
return current
```

**Важный нюанс**: у узла может быть несколько родителей (это DAG). `get_root`
всегда идёт через `parents[0]` — первого зарегистрированного родителя. Для
узла с несколькими путями наверх это детерминированный, но не единственно
возможный «корень» — просто тот, что достижим через цепочку первых
родителей. Если структура графа предполагает несколько независимых путей
наверх с разными фактическими корнями, `get_root` даст только один из них.

## `get_fqn(node)`

Строит «путь» узла как `id`-ы всех предков через `parents[0]`, начиная от
корня, соединённые `/`: `"root/pipeline_a/task_1"`. Та же оговорка, что и
у `get_root` — путь строится только через первого родителя на каждом
уровне, не отражает альтернативные пути в DAG с несколькими родителями.

## `get_depth(root)`

```python
depth = 1
current = root
while current.children:
    depth += 1
    current = current.children[0]
return depth
```

**Это не глубина дерева/графа в общепринятом смысле (не длина самого
длинного пути).** Функция идёт только по `children[0]` на каждом уровне —
это глубина одной конкретной ветки (первого ребёнка на каждом уровне), а
не максимум по всем веткам. Для несбалансированного дерева, где самая
длинная ветка не является первой веткой ни на одном уровне, `get_depth`
вернёт заниженное число. Это задокументированное ограничение, а не
предположение — в коде нет обхода всех веток с взятием максимума; это
стоит явно учитывать перед использованием `get_depth` как «настоящей»
глубины графа. Смотри также [design_decisions.md](design_decisions.md).

## `get_leaves(root)` / `get_flat_list(root)` / `get_size(root)`

Все три построены поверх `get_flat_list = walk(root, "dfs", "children")`:
`get_leaves` фильтрует узлы без детей, `get_size` — длина плоского списка.
Ни один явно не защищён от повторного посещения общего потомка в DAG с
несколькими родителями иначе, чем через `visited` внутри `walk` — то есть
узел с двумя родителями будет посчитан **один раз**, а не дважды, даже
если он технически достижим двумя разными путями от `root`.

## Обнаружение циклов: трёхцветный итеративный DFS

```python
WHITE, GRAY, BLACK = 0, 1, 2
```

- **WHITE** — не посещён.
- **GRAY** — на текущем пути обхода (предок узла, который раскрывается
  прямо сейчас).
- **BLACK** — узел и всё его поддерево полностью обойдены.

Ребро в GRAY-узел означает, что обход вернулся на уже открытый путь — это
и есть цикл. Реализовано через явный стек кадров `[node, next_child_index]`
вместо рекурсии — по той же причине глубины, что и в `walk`. Возвращаемое
значение при обнаружении цикла — не просто «два узла ребра», а весь путь
цикла: замыкающий узел плюс все узлы текущего стека в обратном порядке —
это сохраняет поведение оригинальной (рекурсивной) реализации, которая
сообщала о полном цикле, а не только о его последнем ребре.

`has_cycles(root)`, `detect_cycles(root)` и `validate(root)` — тонкие
обёртки над `_detect_cycles_iterative`; `validate` дополнительно
возвращает `(bool, list)` кортеж, который `GraphEngine.validate` публикует
как есть в событии `pipeline_validated`.

## Обработка ошибок

Большинство методов `GraphUtils` обёрнуты `@wrap_errors(GraphError,
passthrough=(GraphError,))` — неожиданное исключение внутри превратится в
`GraphError` с сохранённой причиной. Исключение — `find_node`: он **не**
поднимает исключение при некорректном `node_id`, а логирует ошибку и
возвращает `None`. Это осознанная асимметрия: `find_node` в остальном коде
(`BasePipeline.find_task`, `GraphEngine.find_node`) везде используется в
контексте «может не найти» — превращение невалидного входа в `None`, а не
в исключение, избавляет вызывающий код от дублирующегося try/except там,
где отсутствие результата и так штатно обрабатывается.
